1.4 这个产品不做什么

不做为什么（这是设计决定，不是待办）
不训练 / 不微调 / 不改权重RSI 的载体是 harness，不是参数；权重冻结让「收益归因于外挂」成立
不改 Codex / OpenCode 本体执行器是 substrate；改动只发生在它暴露的可编辑面（AGENTS.md / skills / hooks 等）
不内置 rubric / 答案answer-free 是核心假设：真实工作里没人给你打分；引入 rubric 就等于把它变成刷题机
不做在线服务 / 多租户当前形态是批处理 CLI + 文件系统；并发只是进程内线程池
不保证「通用 harness」任务级 harness 允许写死本任务事实；通用性只承诺在「过程」层
不提供安全沙箱这是当前实现的缺口，不是卖点；§7.10 给出加固路径

1.5 坐标系：同类工作在做什么

三类相邻工作，差别不在「是否自我改进」，而在改什么、用什么信号、是否要求真值、是否持久化。下表是本文档作者的理解，不是对原文的引用。

谱系改什么信号要真值？持久化
权重层 RSI（自训练、自博弈、DGM 式自改代码）参数或程序本身验证器 / 测试 / 环境奖励要权重或程序快照
Harness 优化（提示词/流程搜索类工作）提示词、少量流程任务分数或偏好模型要（或代理指标）提示词集合
评测 harness（跑分框架）不改，只测量基准分数要运行日志
Harness²八组件整棵树同任务上的行为对照 + 证据追溯不要任务级树 + 领域经验库

关于「第一个」：仓库 README 只写 recursive agent harnessing，没有「first RSI」字样；「Harness 层的 RSI」「第一个」是论文/媒体口径。同期还有 Video-RSI、PluginRSI、metaRSI 等工作都打 RSI + harness 旗号——「第一个」当营销看，机制才值得读。

2.1 Harness 与 c1–c8

harness = 模型之外让它成为 agent 的那层系统。Harness² 只把这一层当作优化对象，并把它的可编辑部分切成 8 个组件（代码里叫 c1..c8，实际是两个 SurfaceSpec 的值）。

c1系统提示词systemprompt.mdAGENTS.md常驻
c2护栏guardrails.mdAGENTS.md常驻
c3记忆LongTermMEMORY.mdAGENTS.md常驻
c4工具说明tool_descriptions/tool_guidance.mdAGENTS.md常驻

常驻预算是最硬的约束：OpenCode 四个常驻文件合计 ≤ 24,000 字符；Codex 只有 AGENTS.md，≤ 8,000 字符（Codex 自身还会在 32,768 字节处静默截断）。超限 → 校验失败。这就是为什么提示词反复强调「加一条常驻，就删一条」。

c2–c4 在 Codex 上不是四个文件：Codex 的常驻面只有 AGENTS.md，护栏/记忆/工具说明是同一文件里的不同职责段落；表里并列是为了概念对齐，不是路径对齐。

2.2 两级递归

任务级递归（内层）：在当前任务上做对照实验。基线 k 次 → 提案 2k 个 → 每个候选 probe 1 次 → 合成 k 个终版 → 盲选 1 个。

它回答：「这个任务上，改哪里能让行为变好？」

Harnessing 级递归（外层）：任务结束后，用完整记录（所有候选的树、轨迹、产物、决策笔记）diff 出「哪条改动起了作用」，写成一条可迁移经验，存进该领域的库。

它回答：「下次遇到同类任务，应该先想到什么？」

任务 tbase harness + 同领域库
→
内层：Propose–Probe–Compose产出被采纳的树
→
盲选只看产物
→
外层：反思edits 表 + 一条 lesson
→
任务 t+1仍从 base 起步

注意最后一步：下一个任务不会继承上一个任务改好的树（代码里写死从 adapter.base_harness() 读取）。继承的只有库里的经验文本。这是整套设计里最重要的一条反污染约束。

2.3 Propose–Probe–Compose

① Proposek 个 INV + k 个 DOM，各自独立采样
→
② Probe每个候选在同一任务上真跑 1 次
→
③ Composek 个合成器看全量证据，各产出一个终版
维度管什么典型改动
INV（不变式）agent 怎么工作，跨任务都该成立流程顺序、校验、停止条件、工具使用纪律
DOM（领域）从业者才知道的东西法域时限、财务口径、交付件格式约束
AGG / COMPOSE合并与取舍merge、整体采纳、KEEP_BASE、还原更早的 checkpoint

三条硬约束：① 每处改动必须能追溯到轨迹里的一个具体瞬间；② 每条候选只有 1 次 rollout，单次结果只能算弱证据；③ 关联的 rollout 什么都没产出时，该改动被判 UNSAFE，除非其余证据压倒性。

2.4 可编辑面与编辑契约

提案不改整棵树：没写的文件就是继承（omitted-is-inherited）。可写路径由正则白名单决定，越界文件不是被静默丢弃，而是整棵提案作废并反馈给模型重试一次。

路径模式允许说明
systemprompt.md / guardrails.md / LongTermMEMORY.md / tool_descriptions/tool_guidance.md是常驻文本
skills|.agents/skills/<name>/SKILL.md是名字限 [a-z0-9][a-z0-9_-]*
skills/<name>/scripts/*是技能自带助手；放错位置等于不存在
sub_agents/<name>/AGENT.md是部分基准/执行器关闭
scripts/*.py是保留名不可覆盖
plugin/<name>.ts · .codex/hooks.json是OpenCode plugin / Codex hooks
harness2/**、任务数据、评测器、其他任务的库否路径根本不在白名单里；写了 → 整棵拒绝
校验通过（在 rollout 之前）
  • 常驻长度 ≤ 上限；Codex 的 AGENTS.md 不得为空
  • 每个 skill 有 description、名字规则正确、且被 always-on 点名
  • 子代理 frontmatter 合法；被禁时直接报错
  • Python 能编译；脚本引用都存在；保留脚本未被顶替
  • hooks 是合法 JSON、事件在白名单、类型必须是 command
  • benchmark 自己的 validate_tree 通过
  • 树里没有 grader 标记（7 个 marker）
任一条失败

不是丢弃单个文件，而是整棵提案不采纳；错误原文（可操作的话术）回灌给模型，重试 1 次（STAGE_ATTEMPTS=2）。

仍失败 → 回退到当前 harness，阶段记 fell_back 与 error。任务继续，不中断。

另外还有 autotrigger()：新技能没在常驻文本里被点名时，自动补一行触发词（如果补完不超预算）。它修的是「技能被静默丢弃」这类最难查的错。

2.5 证据协议

证据是磁盘上的文件，prompt 里只有一段指针（MISSION.md）。所以长轨迹不会被压成摘要，模型可以自己 grep/翻页。

路径内容谁读
context/task.md任务原文（已剥离评分标准与期望输出）提案 / 选择 / 反思
context/source/源材料，按 leak_globs 过滤答案键提案 / 选择
context/rollouts/<label>.md完整轨迹，统一 [ACTION]/[OBSERVATION]/[ERROR]提案 / 反思
context/deliverables/<label>/产物，用判分器同款 extractor 渲染提案 / 选择
context/harness/正在编辑的树（提案的工作副本）提案
context/library/同领域历史：完整树 + EXPERIENCE.md提案 / 反思
context/pool/<label>/候选 harness + 它的 rollout + unified diff合成器
context/decisions/每个阶段的 <notes> 决策记录合成器 / 反思

三道路障：① leak_globs 命中答案键路径 → 进上下文前抛错；② GRADER_VERDICT_MARKERS 七个标记（pass_rate、passed_count、deterministic_eval_* 等）出现在文件名或内容 → 抛错，并明确写着「这是泄漏，不是误报」；③ 产物必须能被判分器读出来，读不出来的产物不算漂亮。

2.6 盲选与采纳

选择者只看产物：候选被匿名成 A/B/C…（按 task/mode/k 的 sha1 种子洗牌，可复现），看不到 harness、看不到 run、也看不到哪个是基线。

规则值含义
候选池仅 finalsagg1..aggk 或 c1..ck；基线不入池，因此没有「不选」这个选项
k=1trivial selection只有一个终版 → 不开选择会话（省一次调用）
非交付物先丢没产物 / 渲染失败 / 空内容 → dropped
选择失败回退finals-only 池里没有基线可退：退到排序第一个 final，并记 fallback（mixed 池才可能退基线）
判分之后选择提交后才判分；判分失败 = unscored，不当 0

7难题与解决方案

本章回答十个真问题：无真值、过拟合、通用性、有效性、膨胀、学习信号、越权、泄漏、成本、安全。每节都写「现在怎么做 / 残留缺口 / 最小加固」。缺口是这套方法的一部分，不藏。

读法：这一章不是营销页。每节的「残留缺口」都是当前代码里真实存在的限制，「最小加固」是可以在不改架构的前提下做的事；「验收信号」是你加固之后应该观察到的变化。如果只能做一件事，先做 §7.4 的候选重复采样。

7.1 没有标准答案：信号从哪里来

真实专业任务没有 rubric、没有单元测试、没人给你打分。没有分数，怎么知道改对了？

做法机制代价 / 边界
行为对照同一任务上，基线 k 次 rollout 与候选 rollout 的差异就是信号；重复失败=真问题，分歧=最便宜的收益没有统计显著性；单次差异可能是采样噪声
证据可追溯每处改动必须点名轨迹里的一个瞬间；说不出来就是猜测「瞬间」由模型自己指认，可能指错
answer-free提示词明确「没有 rubric / 答案 / 分数，不要猜 grader 想要什么」；RunView 不携带分数；判分在选择之后最终「好不好」仍是一个模型判断
绊线7 个 grader 标记（pass_rate 等）出现在证据里 → 抛错，不静默只防显式泄漏，不防模型自己推断

最小加固：把「行为对照」结构化——数值类产物做数值 diff，文本类做关键字段 diff，而不是全靠模型读轨迹。验收信号：同一改动在两个独立 judge 下结论一致率上升。

7.2 单任务过拟合：怎么知道这不是只对这一个任务有效

为修一个任务把 harness 魔改一通，下一个任务换题型，改动全成累赘。这是 RSI 最经典的翻车方式。

机制怎么起作用代码/提示词位置
基线是分布k 次同一 harness 的 rollout；只在 1/k 出现的失败是噪声，照着改就是过拟合prompts.aggregate「a defect in 1/k is noise」
事实 / 过程分层本任务事实允许写死（标注 in this workspace）；过程必须写成对该领域都成立prompts.GENERALIZE
不继承树下一个任务仍从 adapter.base_harness() 起步；继承的只有库里的经验文本schedule.run_task
库是假设抄来的组件必须重新验证它的 workspace 事实；上一个任务的映射不是事实prompts.GENERALIZE + library
KEEP_BASE「不改」是一等答案：没有证据支持的适配记为一等失败_KEEP_BASE

残留缺口：① 每个候选只有 1 次 rollout，n=1 的判断本质是「单样本对照」；② k=1 时「重复失败」信号不存在（1/1 全是噪声），只剩可追溯性；③ 循环内没有留出任务回灌，过拟合只能靠事后评测发现。

最小加固：对 top-1 候选（或全部候选）做 n=2 重复 probe，只有两次都复现的行为差异才允许写进终版；把 --split-file 的 test 集固定为「只评估、不进库」。验收：train 增益与 test 增益的差距缩小。

7.3 通用性：跨任务还能用吗

设计作用边界
INV / DOM 分维「怎么工作」与「行业知识」分开提，合成时是合并而不是折中两个维度都可能被写成任务特定
领域库检索按 domain 物理隔离，只给同领域历史领域内部也可能高度异质
cue 写法要求写「情境的形状」，不是任务事实；太泛/太窄都被点名反对没有下游验收，cue 质量靠模型
留出评估scripts/split_tasks.py 做领域分层切分（默认 train 0.5）测度，不是运行时保证

残留缺口：运行时没有任何「换一个任务还成立吗」的检查；跨领域迁移也没有专门实验。所谓通用性，一半靠设计（分层），一半靠评测（留出集）。

最小加固：入库时要求 cue 至少能映射到 2 个不同任务形态（让模型自证并记录）；在 library 增加「被后续任务引用/命中」计数。验收：同域新任务的首轮增益；跨域使用时性能不下降。

7.4 有效性：怎么证明真的更好，而不是运气

层机制它排除的可能
改动是否改变行为每个候选 probe 1 次，同任务、同模型「只是改写了措辞」
改完是否更好盲选：匿名候选、只给产物、隐藏 harness/run「因为它是改进版所以更好」
改动是否该进终版合成器逐条 merge/drop，证据权重：重复失败 > 单次；下行风险与上行同权；非交付=UNSAFE「把没用的改动洗进终版」
整体是否真的涨判分后置、base/refined 同参、未评分≠0「用分数优化分数」

残留缺口：n=1 的候选、单次判分、选择者与改进者同源、k=1 时根本没有跨候选比较（选择池只有一个终版）。「有效」在样本量上是弱结论，这也是论文用 k 增大来补的原因。

最小加固：① 选择者换成不同模型；② 在池中额外放一个匿名基线产物，用来测「改了是否真的比不改好」（当前设计刻意不放，代价是失去这个对照）；③ 判分做两 judge 交叉。验收：采纳后回滚率下降；与独立 judge 的一致率上升。

7.5 修改膨胀：怎么保证不会越改越大

机制怎么限强度
always-on 硬上限OpenCode 24,000 / Codex 8,000 字符；超限即校验失败硬
触发词税每个新 skill 的名字必须出现在常驻文本里（否则校验报错）硬
形态歧视skill > script > subagent > plugin/hook > 常驻散文；加常驻要「一进一出」提示词
可变小KEEP_BASE、drop/revise、串行模式可还原更早 checkpoint提示词
每任务一条 lesson经验库每任务最多 1 条，逼取舍硬

残留缺口（最该补的一处）：脚本、技能正文、插件、库条目都没有体积/数量上限。一个提案可以在一次编辑里加 20 个 skill；没被引用的脚本允许存在；库随任务数线性增长；而改进者读的上下文要装整棵树 + 整库，不截断——膨胀的代价最终以 token 和时间的形式出现，而不是被拦住。

最小加固：在 BenchmarkAdapter.validate_tree 里加三条基准专属上限：树总字节数、单次提案新增文件数、脚本/技能数量；库加容量与 TTL。验收：每任务树体积的中位数与 P95；常驻文本占 token 比例。

7.6 学习信号：哪些是好的，哪些是坏的

类型信号为什么
好同一任务多次运行之间的分歧能力已存在，只是没被告知——最便宜的收益
好基线上反复出现的具体失败是 harness 的真实属性，不是采样噪声
好轨迹里可见、尚未爆发的风险预防性改动，代价低
好已核实的 workspace 事实基线花代价才发现的，写进去直接省掉最难一步
坏只在 1/k 出现的失败噪声；照着改就是过拟合
坏单个候选的一次好/坏弱证据，不能定因果
坏「看起来是好实践」没有可点名的瞬间，等于猜测
坏多个候选意见一致共同模型偏置，不是独立验证
坏被采纳这件事本身选择比的是产物，不是改动
坏关联 rollout 什么都没产出判 UNSAFE，除非其余证据压倒性
坏一次改多个组件、无执行隔离只能判 confounded，不许编因果

残留缺口：信号的分级全部由模型在执行时判断，没有量化强度，也没有「这条 helped 到底多可信」的数值。edits 表是文本，不可聚合。

最小加固：edits 表加结构化字段 signal_type（divergence/repeat/risk/fact）与 count；helped 只有在「可隔离 + n≥2」时才允许写；其余一律 confounded。验收：edits 表的可聚合率；helped 的事后复查一致率。

改进者会不会改框架代码、改评测、往执行环境里塞可执行文件？——前两个不会，第三个正是它的工作方式。

能改不能改

7.9 成本与复现

已经做到的：预算恒等式 R=4k/P=3k 断言；指纹缓存（证据或路径变化即失效）；原子写 summary + flock；namespace 含 bench/substrate/mode/k/seed/tag；续跑校验产物与 harness 指纹；审计五件套（mission/system/response/meta/workspace）。

提案会话OpenCode：外部目录 deny；Claude CLI：skip-permissions隔离强度取决于通道

结论：当前是内容与路径边界，不是 OS 级安全边界。把它当研究工具，在受控主机上跑；不要在多租户环境直接暴露。

最小加固：容器内执行 + 只读挂载证据 + egress 白名单 + hooks 命令审核；把「无沙箱」写进运行说明（README 已有一条，但产品界面也应显示）。验收：逃逸测试；网络阻断；每次 run 的权限清单。

9常见问题

Q1 · 它真的是「第一个 RSI 的 harness 框架」吗？

仓库没有这句话。README 的自我描述是 recursive agent harnessing；「Harness 层的 RSI」「第一个」来自论文/媒体。同期 Video-RSI、PluginRSI、metaRSI 等都在做相邻的事。结论：把它当「把 RSI 挪到 harness 层并跑通专业基准」的工作，不要当首创声明。

Q2 · 它会改我的框架代码，或者往代码里加工具吗？

框架代码、评测器、任务数据、rubric 都不会（不在白名单，写了整棵提案作废）。但它会往 harness 里加可执行文件：scripts/*.py、plugin/*.ts、.codex/hooks.json——这正是「加工具」的实现方式。且没有内容审查（§7.7）。

Q3 · 为什么 k=1 也要 8 次调用？

4 次 rollout（1 基线 + 2 候选 + 1 终版）+ 3 次编辑会话（INV/DOM/合成）+ 1 次反思 = 8。选择会话在 k=1 时被跳过（只有一个终版，没有可比较的候选）。

Q4 · 库里存了完整 harness，为什么不直接拿来做下一个任务？

那会把上一个任务的过拟合原样搬过去。当前设计是：库只作为证据，下一个任务从 base 起步；要用某个组件，必须复制并重新验证它的事实（§2.7）。

Q5 · 为什么判分要放在最后？不能拿分数指导改进吗？

真实工作里没有分数。用分数指导改进会把方法退化成「对着评测器调参」；放在最后是为了让「选择」和「测量」分离，且未评分不会被当成 0（§2.6）。

Q6 · 能换模型 / 换执行器吗？

都能。求解模型与改进模型分离配置；执行器 --substrate oc|cx；换执行器等于换一套可编辑面与基线，结果不可与另一套直接比较。

Q7 · 为什么 Codex 跑的时候沙箱是关的？

为了让 hooks 生效、让树里的脚本可执行。--dangerously-bypass-approvals-and-sandbox 与 --dangerously-bypass-hook-trust 是当前实现的前提，也是它最大的安全缺口（§7.10）。

Q8 · 数据存在哪？需要数据库吗？

不需要。全部是 runs/、library/ 下的目录与 JSON；一致性靠原子写与 flock。§3.6/3.7 的逻辑表是查询视角，不是物理 schema。

Q9 · 为什么不直接把 rubric 给它，让改进更准？

那会让它在真实场景失效——真实场景没有 rubric。answer-free 是方法假设，不是偷懒（§7.1）。

Q10 · demo 不调模型，能证明什么？

证明流程、校验、账本、选择、反思、入库都通，以及「行为对照」确实能定位到一行代码。它不证明模型能力，也不产生可比的分数。

Q11 · 能加自己的基准吗？

实现 BenchmarkAdapter 的十余个方法 + 一个 BenchSpec 值即可（§3.5）。注意：答案键路径必须在 leak_globs 里声明，产物读取要和判分器一致。

Q12 · 为什么预算是 4k / 3k，而不是别的数？

因为一次完整对照实验的最小构成：k 基线 + 2k 候选 + k 终版 = 4k 次 rollout；k INV + k DOM + k 合成 = 3k 次编辑。断言它，是为了让「跑完了」可验证（§2.8）。

Q13 · 为什么选择池里没有基线？那怎么知道「改」比「不改」好？

当前约定是「k 个终版里必选一个」，用合成器的 KEEP_BASE 表达「不改」。代价是失去「改 vs 不改」的直接对照——这是 §7.4 指出的缺口，也是加固建议里最值得做的一条。

Q14 · 断点续跑会不会重复花钱？

不会重复花同一笔：调用有内容指纹缓存；任务级续跑会校验产物、harness 指纹与 summary 覆盖的模式。但失败重跑、换 seed/换 models 会重新计费。

Q15 · 库会不会越积越多？

会。每任务最多一条，但任务多则条目多，且每条带完整树；库没有容量上限（§7.5）。这也是上下文成本的主要来源之一。

Q16 · 它到底能提升多少？

README 报告单步增益：WorkBuddy-Bench +11.5、JobBench +4.5、LAB Partial +11.8 个百分点；k 增大继续涨。这些是论文口径，不是本仓库 demo 的读数；复现要严格同参（§5.5）。
